# AI flow — три кроки AI-аналізу оголошень

High-level огляд усіх AI-кроків OLX Dashboard: як влаштовані агенти, що спільного між кроками,
і куди дивитись у коді. Детальні специфікації — `docs/plans/*`; модулі/ендпойнти —
`docs/architecture.md`.

## Три кроки (усі — ЛИШЕ вручну, ніколи не авто)

| # | Крок | Кнопка | Що робить | Пише в |
|---|------|--------|-----------|--------|
| 1 | **AI Фільтр (релевантність)** | «AI Фільтр» | Класифікує кожен лот: чи він ПРОДАЄ цільовий товар (а не чохол/запчастину/згадку сумісності) | `listings.ai_relevant` |
| 2 | **AI Аналіз (мінуси/плюси)** | «AI» | Знаходить у описах пункти-мінуси / пункти-плюси за критеріями пошуку | `listings.cons` / `pros` |
| 3 | **AI Вибір (ранжування)** | «AI Вибір» | Обирає ТОП-N найкращих кандидатів (без явних мінусів) і ранжує їх | `listings.ai_rank` / `ai_pick_reason` |

Спільні інваріанти всіх трьох:
- **Ніколи не авто** — лише за кнопкою; жоден скан / автооновлення / cron їх не тригерять.
- **PII продавця в промпт не йде** (тільки `id/title/params/description`, для кроку 3 ще `price/city/pros`).
- **Обсяг** — єдиний `ScopeSelector` (весь пошук / у таблиці / вибрані / найкращі кандидати),
  `docs/plans/ai-scope-selector.md`.
- **Два рівноправні рушії** (нижче): авто (OpenRouter) і ручний (ZIP-пакет для агента).
- **Ключ OpenRouter** — лише в `server/.env` (`OPENROUTER_API_KEY`), опціональний.
- **Промпти — єдине джерело** у `server/src/analysis/` (спільне для авто й ручного).

## Два рушії (для кожного кроку)

### Авто (OpenRouter)
Доступний, якщо є `OPENROUTER_API_KEY`. Сервер сам дрібними батчами викликає LLM, парсить і
верифікує відповідь. Дефолтна модель — `google/gemini-2.5-flash-lite`. Інлайн-промпт (оголошення
вставлені в текст) → відповідь JSON у чаті → сервер парсить.

### Ручний (ZIP-пакет) — уніфікований агентний флоу
Без ключа. Кнопка «Завантажити ZIP-пакет» віддає архів із `prompt.txt` + даними (+ для кроків 1–2
готові Python-скрипти). Промпт розрахований на **агента з файловою системою** (Antigravity CLI,
Claude Code), часто зі слабкою моделлю, тож усі три кроки використовують **один патерн**:

> **МЕХАНІЧНА процедура на файлах** — не дослідницьке завдання. **Map** по чанках у проміжні
> файли (по одному чанку — не впираєшся в ліміт відповіді, переживає втрату контексту) →
> **Reduce** → результат у **`output.json`** → користувач вставляє **ВМІСТ `output.json`** у
> застосунок. **Нічого в консоль.** Жорсткий список **`СУВОРО ЗАБОРОНЕНО`** (не створювати зайвих
> файлів/скриптів, не «досліджувати» датасет, не ітерувати) свідомо прибирає латитуду, через яку
> слабкі моделі зациклюються. Наприкінці — **Fallback** для асистента без відповідної файлової дії
> (зробити все за один прохід і повернути JSON у відповідь).

Спільні блоки промпту (`МЕХАНІЧНА процедура`, `Вміст пакета`, `СУВОРО ЗАБОРОНЕНО`, `РЕЗУЛЬТАТ`,
`Fallback`, пункти-заборони) винесено в **`server/src/analysis/manualZip.ts`** — кожен крок
компонує звідти, а не дублює текст.

### Чим кроки відрізняються в ручному режимі

| Крок | Скрипти в ZIP | Map (по чанку) | Reduce | Хто пише `output.json` |
|------|---------------|----------------|--------|------------------------|
| 1. Фільтр | `merge.py`, `verify.py` | класифікація → `classifications/result-NNN.json` | `python merge.py` + `python verify.py` (перевірка покриття id) | `merge.py` |
| 2. Мінуси/плюси | `analyze.py` (детермінований regex-движок) | — (агент лише пише `patterns.json` з мовних знань) | `python analyze.py` **раз** (масовий прохід, відкидає заперечення, дістає evidence) | `analyze.py` |
| 3. Вибір | **немає** | номінація → `nominations/nominees-NNN.json` | агент читає всі nominees і сам обирає фінальний ТОП-N | **сам агент** |

**Чому крок 3 без скриптів:** відбір/ранжування — це **судження**, тож детермінованого движка
(як `analyze.py`) бути не може; а механічний збір (як `merge.py`) не потрібен, бо фінальний
reduce — теж судження, яке агент робить сам, читаючи невеликі nominees-файли. Крок 3 лишається
файловим (map у `nominations/`) заради стійкості до втрати контексту, але **без жодного `.py`**.

## Що спільне і де воно в коді

- **Спільні фрагменти ручних промптів:** `server/src/analysis/manualZip.ts`
  (`mechanicalIntro`, `packageContents`, `forbidden` + `FORBID_*`, `resultLine`, `fallbackBlock`,
  `OUTPUT_FILE`).
- **Крок 1 (Фільтр):** `server/src/analysis/relevance.ts` (`buildRelevancePrompt` /
  `buildRelevanceZipInstructions` / `prefilterCandidates`), скрипти `relevance_merge.py` /
  `relevance_verify.py`, роут `server/src/routes/relevance.ts`, план
  `docs/plans/semantic-relevance-filter.md`.
- **Крок 2 (Мінуси/плюси):** `server/src/analysis/prompts.ts` (`buildMatchingPrompt` /
  `buildManualZipInstructions`), рушій `analyze.py`, парс `parse.ts`, роути
  `server/src/routes/analysis/*`, план `docs/plans/llm-analysis.md`.
- **Крок 3 (Вибір):** `server/src/analysis/aiPicks.ts` (`buildPickPrompt` /
  `buildPickManualZipInstructions` / `parsePickResponse`), роут `server/src/routes/aiPicks.ts`,
  план `docs/plans/AI-auto-top.md`.

## Майстер «Мінуси/плюси» (крок 2) — 4 кроки UI

1. **Критерії.** Обрати режим (мінуси/плюси) та обсяг (`ScopeSelector`). Критерії можна
   згенерувати авто/вручну або додати власні → `searches.analysis_criteria` (JSON `{cons:[],
   pros:[]}`).
2. **Пошук (matching).** Знайти збіги критеріїв у описах (авто або ручний ZIP).
3. **Перевірка.** Переглянути знайдені пункти; тегами вмикати/вимикати. Пунктирна рамка =
   `evidence` не підтверджено як підрядок опису (анти-галюцинація; `evidence` у БД не зберігається).
4. **Запис.** «Додати до наявних» (дефолт — мерж без дублів) або «Перезаписати» (з попередженням).

## Інваріанти

- Зміна `title`/`description` після аналізу → `analysis_stale=1` (бейдж «застарілий аналіз»),
  без авто-переаналізу.
- Мінуси/плюси на рівні оголошення (`listings.cons`/`pros`, TEXT `• пункт\n• пункт`), сумісно з
  ручним едітом у `ProsConsCell`. Критерії — на рівні пошуку.
- Ручний override вердикту (`ai_relevant` / статус / ранг) не перетирається авто-прогоном.
