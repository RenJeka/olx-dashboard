# План: замір етапів великого пошуку (S17, тимчасові логи)

> **Статус:** 🟢 активний (з 2026-10-04) · лише замір, без лагодження (рішення людини 2026-10-04)

## Контекст

S17 ([stability-baseline](stability-baseline.md)): на пошуку `iphone` (`search_id = 4`) `GET /listings` і пошук
в описі відповідають ~17–20 с. Логи Render (2026-10-04) показують, що майже весь час іде на сервері: Fastify
`responseTime` `/listings` — 20,1 с, пошук — 17–18 с. CPU API під час запитів — помітно нижче за ліміт 0,15 ядра,
тож гіпотеза «гальмує CPU» слабшає. Нова гіпотеза (середня впевненість): сервер чекає доставки й розбору рядків
із Turso.

Мета — розкласти час на етапи. Лагодження — окреме рішення людини після висновку.

## Файли

- `server/src/routes/listings.ts` — тимчасові логи тривалості етапів у `GET /api/searches/:id/listings` і
  `GET /api/searches/:id/listings/search` (рівень info, scope `perf`, лише stdout — у `app_logs` / Turso не
  пишеться; додаткових запитів до БД немає).
