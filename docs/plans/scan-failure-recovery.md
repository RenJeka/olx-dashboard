# Стійкість великих сканів: інкрементальне збереження + порятунок часткових даних

## Контекст / проблема

Великий глибокий скан (сотні запитів до OLX, ~1 година) інколи падає майже наприкінці,
і **все зібране втрачається** — у БД не потрапляє нічого. Причини (за кодом):

1. **All-or-nothing запис.** `upsertListings` викликається один раз — у `finalizeScanResult`,
   ПІСЛЯ завершення всього фетчу. Весь скан живе в пам'яті; будь-який виняток дорогою →
   `withScanRun` пише `error` у `scan_runs` і викидає все зібране.
2. **Цикл варіантів (синонімів) не рятує вже зібране.** У `fetchAllQueries` (звичайний/deep
   скан) і `runDeepScanFromPlan` (двофазний) збій ОДНОГО пізнього варіанта — GraphQL впав на
   `offset=0` (напр. HTTP 403 анти-бот після сотень запитів; 403 детермінований, не
   ретраїться) І HTML-fallback теж впав (той самий анти-бот) — валить увесь скан разом із
   сотнями оголошень, зібраних попередніми варіантами.
3. **Бісекція цін без захисту.** `SplitScanner.bisectPriceRange` викликає `fetchPage` без
   try/catch: один викид посеред бісекції (після вичерпаних ретраїв або 403) валить весь
   варіант, хоча частина бакетів (з уже завантаженими `page0`) готова.
4. (Побічно знайдено) `runDeepScanFromPlan` викликає `scanFromPlan` **без `deep: true`** —
   для `noSplit`-варіантів це делегує `fetchSearch` у ЗВИЧАЙНОМУ режимі (3 сторінки замість
   до 26): недозбір «малих» варіантів у скані за планом.
5. (Захисне) фінальний `db.batch` — тисячі statements одним запитом; на великих сканах це
   великий мережевий payload до Turso — чанкуємо.

## Рішення

**Інкрементальне збереження (`ScanPersister`)**: зібрані оголошення upsert-яться в БД
ітераціями по ходу скану — після кожної сторінки deep-скану, кожного цінового бакету і
кожного варіанта запиту. Якщо скан падає/переривається — все, що вже пройшло flush,
ЛИШАЄТЬСЯ в БД (upsert по `olx_id` ідемпотентний; повторний прохід тих самих рядків —
дешевий touch із throttle, Turso-бюджет не роздувається). Плюс **порятунок часткових
даних**: збій пізнього варіанта/бісекції завершує скан частковим успіхом (`partial` +
`warning`), а не помилкою.

Інваріанти, що НЕ змінюються: вікно покриття (auto-disable) як і раніше запускається лише
для повних успішних GraphQL-сканів (часткові/врятовані скани його пропускають); звичайний
(≤3 запити) одно-query скан пише в БД один раз, як і раніше (без зайвих Turso-записів на
автооновленні).

## Файли

- `server/src/scanner/scanPersister.ts` — **новий**: клас `ScanPersister` (дедуп
  уже збережених `olx_id`, накопичення `found`/`new_count`, `flushSafe` для проміжних
  флашів, `flush` для фінального).
- `server/src/types/scan.ts` — `FetchOptions.onListings?` (колбек інкрементального
  збереження, викликається фетчерами з новозібраними оголошеннями).
- `server/src/scraper/graphql/split.ts` — `scanBuckets`: flush `rootItems` + після кожного
  бакету; `bisectPriceRange`: try/catch → перерваня бісекції частковим набором бакетів.
- `server/src/scraper/graphql/types.ts` — `SplitPlan.probeWarning?`.
- `server/src/scraper/graphql/fetcher.ts` — `fetchSearch` (deep): flush після кожної
  сторінки; `scanFromPlan`: прокидання `onListings` у `scanBuckets` + `probeWarning` у
  warning.
- `server/src/scanner/fetchOrchestrator.ts` — `fetchAllQueries`: try/catch на варіант
  (збій пізнього варіанта → warning + достроково завершити, зібране лишити) + flush після
  кожного варіанта.
- `server/src/scanner/analyzeScan.ts` — `runDeepScanFromPlan`: той самий порятунок
  варіанта + persister + `deep: true` у `scanFromPlan`; `analyzeVariant`: прокидання
  `probeWarning` у warnings звіту.
- `server/src/scanner/runScan.ts`, `server/src/scanner/scanFinalize.ts` — створення
  persister, фінальний flush у `finalizeScanResult` (лічильники з persister).
- `server/src/scraper/normalizer.ts` — чанкування `db.batch` (захист від гігантського
  payload).
- `docs/architecture.md`, `docs/structure.md` — оновити.

## Test-cases (ручні)

1. **Збій пізнього синоніма.** Пошук із ≥2 синонімами; зімітувати падіння GraphQL+HTML на
   2-му варіанті (напр. вимкнути мережу під час його сканування). Очікувано: скан
   завершується з warning «збій … завершено достроково», дані 1-го варіанта в БД,
   `scan_runs.error` порожній, `warning` заповнений.
2. **Падіння процесу посеред deep-скану.** Вбити сервер посеред глибокого скану великого
   пошуку. Очікувано: у БД вже є оголошення пройдених бакетів/сторінок (перезапуск →
   таблиця не порожня), хоча scan_run лишився незавершеним.
3. **Регресія: звичайний скан.** Малий пошук без синонімів, звичайний скан. Очікувано:
   поведінка як раніше (один запис, вікно покриття працює, disabled_count чесний).
4. **Регресія: зупинка користувачем.** «Зупинити» посеред deep-скану → часткові дані
   збережені, скан `partial`, як і раніше.
5. **Двофазний скан: noSplit-варіант.** Аналіз → запуск за планом для пошуку, де варіант
   має 200–900 оголошень (noSplit). Очікувано: варіант допагіновується до кінця (раніше —
   лише 3 сторінки).
6. **Бісекція з збоєм.** Якщо посеред бісекції OLX почав відбивати запити — скан
   продовжується по вже знайдених бакетах, warning «бісекцію цін перервано», скан partial.
