# План: глибокий скан не гине від засинання Render (S9)

> **Статус:** ✅ виконано (2026-10-03) · PR #36; перевірено на проді (скан 29 закрито стартом, deep-скан 31 `iphone` із закритою вкладкою — 679/679 за 34 хв). Не перевірено на проді: зупинка пінгів після скану (покрито Vitest).

## Контекст

S9 з [stability-baseline](../stability-baseline.md). Перевірка на проді 2026-10-02:

- Скан 27 (`mac mini`, deep, ~2 хв) — ✅ завершився.
- Скан 29 (`iphone`, deep, 681 запит) — ❌ зупинився на 526-му запиті без помилки. Останній поллінг
  `scan-status` від браузера — 13:20:45 UTC, останній лог процесу — 13:35:43 (рівно +15 хв), подій
  Render (OOM/failure/restart) немає, пам'ять 150–180 МБ з 512. Причина (висока впевненість): free-інстанс
  Render засинає після 15 хв без вхідних запитів. Поллінг фронту (`refetchInterval`, TanStack Query)
  ставиться на паузу у фоновій вкладці / при заблокованому телефоні; сам скан іде всередині одного
  довгого HTTP-запиту, який вхідним трафіком не рахується.
- Інкрементальне збереження спрацювало: усе зібране до обриву лишилось у БД.
- Рядок `scan_runs` обірваного скану лишається без `finished_at` назавжди («вічний» скан) — сервер на
  старті таких не закриває.

Рішення людини (2026-10-03): **самопінг сервера під час скану** + **закриття обірваних сканів на старті**.
Не робимо: поллінг у фоновій вкладці, платний тариф.

## Відомі обмеження

- CLI-скан (`npm run scan`) на тій самій БД, що й сервер, буде закритий як обірваний, якщо сервер
  перезапуститься під час нього. Single-user, рідкісний сценарій — прийнято.
- Самопінг тримає інстанс активним лише під час скану; ліміт free-тарифу (750 год/міс на акаунт)
  не загрожує.
