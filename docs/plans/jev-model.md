# План: «модель JEV» — документація, встановлення, пілот для AI-кроків 1+2

> **Статус:** 🟢 активний · етапи 0–1 ✅ (пілоти 2026-10-04) · етап 2 ✅ (на проді з 2026-10-06, PR #63) · етап 3 (діагностика мінусів у Jev) — наступний

## Context

Людина хоче використати Jev (TypeSafe, decision-модель через OpenRouter) у AI-кроках 1 (фільтр
релевантності) і 2 (мінуси/плюси), щоб **здешевити без втрати якості**. Стабільність і харнес закриті
(`docs/current.md`), «модель JEV» — наступна фіча.

Що з'ясовано з документації (jevai.org/docs·agent·mcp·skills, OpenRouter jev-tutorial, jev-classification,
Decisions API reference, docs.typesafe.ai state/models/jaggedness):

| Факт | Наслідок |
|---|---|
| Jev — не LLM: лише typed-відповіді `noul` (ймовірність «так»), `choice`, `score`; без тексту й пояснень | Немає `reason` (крок 1) і `evidence` (крок 2) |
| $0.042 / 1M **вхідних** токенів, вихід безкоштовно; у відповіді `usage.cost` | Вартість = `state` + текст питань |
| Один `state` на запит; `state` обробляється раз, усі питання паралельно; ліміт 32k (state + найдовше питання) | Батч «12 оголошень на виклик» неможливий → паралельні запити (concurrency ~8, retry на 429/5xx) |
| Англійська — основна; інші мови «з нижчою точністю» | Обов'язковий пілот на наших UA/RU описах |
| Точність падає від зайвого тексту в `state`; не рахує, не генерує | Скорочений `state` = дешевше й точніше; генерація критеріїв (крок 2а) лишається на LLM |
| Endpoint `POST https://openrouter.ai/api/alpha/decisions`, `model: typesafe/jev-1.13` (пін), ключ — наш `OPENROUTER_API_KEY` | Без нових залежностей, звичайний `fetch` |
| jevai.org MCP/skills — окремий сервіс із власним ключем (`JEV_API_KEY`) і денною квотою, для **агента** (tool-guard, completion-review…) | До застосунку не стосується |

Рішення людини (2026-10-04): skills+MCP — **глобально**; для рушія Jev — **ймовірність замість
evidence** (поріг noul; LLM-рушій лишається з evidence); шлях A vs B — **пілот обох, вибір за цифрами**;
вибірка — **прод Turso (лише читання)** (переглянуто після заміру — див. етап 1).

Оцінка людини «10 000 запитів × 1000 слів ≈ $1» — правдоподібна (1000 слів UA ≈ 2–2.5k токенів).
Реальні описи вже обрізаються до 1500 символів (`MATCHING_DESC_SLICE`) → очікую ~$0.2–0.3 на 10k для
кроку 1 (гіпотеза, середня впевненість; пілот заміряє).

## Важелі здешевлення (перевіряються в пілоті)

1. **Детермінований префільтр першим** — уже є (`prefilterCandidates` у `server/src/analysis/relevance.ts`), безкоштовно.
2. **Короткий `state` для кроку 1** — назва + характеристики + перші ~300 символів опису (замість 1500).
3. **Шлях A**: крок 1 на короткому state → крок 2 (повний опис, N noul-критеріїв) лише для релевантних.
   **Шлях B**: один запит — повний state + noul «нерелевантне» + N критеріїв.
   Різниця на оголошення: `B − A = (1−r)·N·q − r·S₁`… (r — частка релевантних, q — токени питання, S — state);
   при короткому S₁ гіпотеза — A дешевший (середня впевненість).
4. **Короткі англійські питання** (менше токенів, краща точність); критерії — коротко.
5. **Не аналізувати вдруге**: пропуск незмінених (`analysis_stale`), дедуп однакових описів у межах прогону.
6. **Чистий опис**: `stripHtml` + стиснення пробілів (`server/src/analysis/text.ts`).

### Етап 3 — діагностика кроку 2 (мінуси) у рушії Jev

Спостереження людини (2026-10-06): на пошуку з ~20 мінусами Jev дає 1–2 мінуси на оголошення, хоча в кількох
оголошеннях реально 5–7. Треба побачити, що саме йде в запит і що повертається, перш ніж щось міняти.

**Гіпотези (не перевірені, впевненість низька–середня):**
- поріг `JEV_CRITERIA_THRESHOLD = 0.7` надто високий для багатьох критеріїв (пілот міряв точність на спірних, не повноту);
- формулювання питання `Does the listing state this drawback: "<критерій>"?` — Jev читає буквально («state» =
  прямо написано), українські критерії всередині англійського питання;
- опис обрізано до `MATCHING_DESC_SLICE` — мінуси з кінця довгого опису не потрапляють у state;
- частина критеріїв не потрапляє в запит (перевірити: усі 20 ключів `cons_N` у запиті й у відповіді).

**Кроки**

      зберегти сирий запит (state + питання) і сиру відповідь (noul по кожному критерію) у файл.
- [ ] Інтерфейс моніторингу (live artifact): оголошення → опис → таблиця критеріїв з ймовірностями й порогом,
      підсвітка «знайдено / нижче порогу» і ручна позначка «насправді є».
- [ ] За результатами — рішення людини: поріг по критерію, формулювання питань, довжина state, P-013.
