# План: Redis-кеш для пошуку в описі (тест без ліміту, з логуванням)

> **Статус:** 🟢 активний · [P-011](../parking.md) · код готовий (кроки 0, 2–4); далі — PR, Redis Cloud і тест на проді

## Контекст

P-011: чи дасть користь безкоштовний Redis Cloud як кеш. Людина (2026-10-27): почати з малих пошуків, але **межу
не ставити** — спершу тест із логуванням (скільки МБ займає кожен пошук, коли закінчується пам'ять Redis).

**Прод на 2026-10-27** (Turso, лише читання; 36 921 прочитаний рядок):

| search_id | Пошук | Оголошень | Назви + описи |
|---|---|---|---|
| 4 | iphone | 13 983 | 10,0 МБ |
| 1 | mac mini | 1 841 | 2,9 МБ |
| 2 | кухона шафа навісна | 1 254 | 2,3 МБ |
| 3 | навісна полиця | 1 241 | 2,1 МБ |
| 5 | Ханг Глюкофон… | 139 | 0,25 МБ |

**Ліміти Redis Cloud Essentials Free** (офіційна документація Redis через Context7): 30 МБ пам'яті (разом зі
службовими даними), 30 з'єднань, 100 операцій/с, **5 ГБ мережевого трафіку на місяць**. За замовчуванням політика
витіснення — `volatile-lru`: витісняються лише ключі з TTL; якщо TTL немає, Redis поводиться як `noeviction` —
запис понад ліміт повертає помилку `OOM command not allowed when used memory > 'maxmemory'`, читання працює далі.

### Чому саме пошук в описі і чому двоступенево

Порівняно три способи використання Redis:

1. **Корпус тексту пошуку в Redis + пошук у JS** (обрано). Пошук в описі зараз щоразу читає з Turso всі описи
   пошуку й щоразу чистить HTML (S17, iphone: Turso 7,3–8,1 с + обробка 1,6–2,3 с на запит). Назву й опис пише
   **лише** `upsertListings` (`server/src/scraper/normalizer.ts`) і видалення пошуку — тож скидати кеш треба в
   одному місці, а ручні правки (статус, нотатка, плюси/мінуси) його не чіпають.
   Але тягнути корпус із Redis на кожен запит — дорого по трафіку: mac mini 2,9 МБ × запит → 5 ГБ вистачить на
   ~1 700 запитів/міс. Тому **два рівні**:
   - **L1 — пам'ять сервера** (готовий, очищений, у нижньому регістрі текст): звичайні запити, 0 трафіку.
   - **L2 — Redis** (той самий корпус, стиснутий gzip): лише після засинання/рестарту Render (free засинає після
     15 хв), щоб перший пошук після пробудження не читав усе з Turso.
   - **Версія даних пошуку** — маленький ключ у Redis (`INCR` у `upsertListings` і при видаленні пошуку). L1 і L2
     зберігають версію, з якою їх побудовано; перед пошуком — одне читання версії (байти трафіку). Так кеш
     коректний і тоді, коли скан ішов в іншому процесі (CLI `npm run scan`).
2. **Пошук усередині Redis (Query Engine, `FT.SEARCH`)** — відкинуто: шукає за словами (токенами), а наш
   `matchesQuery` — за підрядком із `&&`/`||`/`!`; підрядок (`*term*`) Redis прямо називає «CPU intensive»,
   індекс займає ще пам'ять із тих самих 30 МБ, а результати розійдуться з таблицею.
3. **Кеш рядків таблиці (`GET /listings`) і варіантів фільтрів** — відкладено до висновку тесту: рядки міняють
   скан, статуси, локальні фільтри, AI, verify, ручні правки (сім місць у коді) — пропущене скидання = старий статус
   у таблиці; браузер і так тримає список до перезавантаження (`staleTime: Infinity`).

Побічний виграш L1 без Redis: локально (порожній `REDIS_URL`) працює лише L1 — повторні пошуки теж без Turso.

### Логування замість ліміту

Межу на розмір не ставимо. Ключі — **без TTL** на час тесту, тож при заповненні Redis не витісняє тихо, а повертає
OOM — і ми бачимо момент і розмір. Кожна операція кешу пише рядок `scope: "cache"` (info, лише stdout — у
`app_logs`/Turso не пишеться):

| Подія | Поля |
|---|---|
| побудова корпусу (промах) | `searchId`, `rows`, `rawBytes`, `gzipBytes`, `tursoMs`, `buildMs` |
| запис у Redis | `key`, `bytes`, `memoryUsage` (`MEMORY USAGE key`), `usedMemory`, `maxmemory`, `evictedKeys` (з `INFO`) |
| пошук | `source` (`L1`/`L2`/`turso`), `ms`, `matches` |
| L1 | розмір L1 (сума `rawBytes`), `rss`/`heapUsed` процесу |
| трафік | накопичено байт від/до Redis з моменту старту процесу |
| скидання | `searchId`, нова версія, причина (`upsert`/`delete`) |

Помилки (OOM, недоступний Redis, таймаут) → `logWarn` (журнал «Журнал» в UI) і пошук іде через Turso — Redis ніколи
не валить запит (інваріант «помилки не валять процес»).
