# Категорії критеріїв мінусів/плюсів: перегляд, редагування, групування синонімів (P-015)

> **Статус:** 🟢 активний · план схвалено 2026-10-10 · [P-015](../parking.md) · код кроків 1–6, 8 готовий (гілка `feat/criteria-categories`); крок 7 (проба Jev) і ручні test-cases не виконані — чекають людину

## Контекст

- Критерії пошуку зараз — плоский JSON `searches.analysis_criteria = {cons: string[], pros: string[]}`. Їх видно
  лише на кроці 1 майстра AI-аналізу; окремого місця для перегляду/зміни/видалення немає.
- Збереження в майстрі (`PUT /criteria`) записує **лише обрані** критерії — необрані зникають зі списку пошуку.
- LLM генерує синонімічні формулювання («тріснутий екран», «дефект екрану», «зламаний екран»); Jev отримує по
  питанню на кожне → дублі, розмиті збіги. Експеримент 2026-10-06 (план `jev-model`, етап 3): частина мінусів
  «macbook m1» — дублі/загальні («експлуатований» ≈ «б/в стан») або характеристики («8 GB»).
- Мінуси/плюси оголошень — текст `• критерій\n• …` у `listings.cons/pros`; від цих рядків залежать: локальні фільтри
  (`searches.local_filters.cons/pros` — рядки), вкладка «Найкращі кандидати» (`cons = ''`), AI Вибір (`pros`),
  варіанти фільтрів (`filter-options`), експорт.

**Мета:** окреме вікно керування критеріями + об'єднання синонімів у категорію; в аналіз (LLM і Jev) іде одна
категорія замість кількох формулювань.

## Дизайн

### 1. Зберігання — той самий стовпець, новий формат JSON (без зміни схеми)

```json
{ "cons": [ { "name": "дефект екрану", "aliases": ["тріснутий екран", "зламаний екран"], "enabled": true },
            { "name": "без торгу", "aliases": [], "enabled": false } ],
  "pros": [ … ] }
```

- Сумісність: елемент-рядок (старий формат) читається як `{name, aliases: [], enabled: true}`. Міграції БД немає —
  нормалізація при читанні, запис завжди в новому форматі. Змінюється лише коментар у `schema.sql`.
- Чому не окрема таблиця: single-user, десятки критеріїв, читаються цілком разом із пошуком → один рядок Turso.
- Унікальність: назви й синоніми в межах режиму унікальні без урахування регістру (синонім не може бути назвою
  іншої категорії).
- Єдиний модуль `server/src/analysis/criteria.ts`: `parseCriteriaConfig`, `serializeCriteriaConfig`,
  `enabledGroups(config, mode)`, `aliasMap(groups)` (синонім/назва lowercase → назва), `remapBullets(text, from, to|null)`.
  Використовують `repo.getSavedCriteria`, роути аналізу, `jevPilot.ts`/`jevProbe.ts` (прибрати їхній власний `parseCriteria`).

### 2. Операції й API

| Ендпойнт | Що робить | Пише в |
| --- | --- | --- |
| `GET /api/searches/:id/criteria` | Конфіг у новому форматі (групи) | — |
| `PUT /api/searches/:id/criteria` | Повна заміна списку режиму: вмик/вимк, додати, вийняти синонім з групи (без зміни оголошень) | `searches.analysis_criteria` |
| `POST /api/searches/:id/criteria/remap` *(новий)* | `{mode, from: string[], to: string \| null}` — **об'єднати/перейменувати** (`to` = назва) або **видалити** (`to = null`) | одна транзакція: `analysis_criteria` + змінені `listings.<mode>` + `local_filters.<mode>`, далі `recomputeFilteredOut` |

- **Об'єднати** `from=[a,b,c]`, `to='дефект екрану'`: група `to` (нова або наявна) отримує синоніми = `from` ∪ їхні
  синоніми − `to`; групи `from` зникають. В оголошеннях пункти з `from` (і їхніх синонімів) → `to`, без дублів,
  порядок пунктів зберігається. `enabled` = true, якщо хоч одна з груп була ввімкнена.
- **Перейменувати** = об'єднання однієї групи (стара назва стає синонімом — щоб нові генерації її поглинали).
- **Видалити**: група зникає зі списку; у діалозі підтвердження галочка «прибрати також з N оголошень»
  (за замовчуванням увімкнена) — тоді пункти видаляються з оголошень і локальних фільтрів.
- Оновлюються лише рядки, де текст справді змінився (Turso: читання `id, <mode>` пошуку з непорожнім полем, запис —
  лише зачеплені). `analysis_at/source/model` не чіпаємо — це перейменування, не аналіз.
- `recomputeFilteredOut(searchId)` (`server/src/scraper/refilter.ts`) — бо після об'єднання фільтр «тріснутий екран»
  стає «дефект екрану» й може зачепити більше оголошень.
- Лічильники «у N огол.» і «зачепить N оголошень» — **на фронті** з уже завантажених `listings` (там є `pros/cons`),
  без додаткових запитів у Turso.

### 3. Аналіз

| Де | Зміна |
| --- | --- |
| LLM-промпт matching (`prompts.ts`) | Список — лише ввімкнені категорії: `1. дефект екрану (сюди ж: тріснутий екран, зламаний екран)`; правило: `criterion` — рівно назва категорії |
| Парс відповіді (`parse.ts`) | `allowed` → мапа синонім/назва → назва: якщо LLM поверне синонім, він зводиться до категорії |
| Jev (`jev.ts`, `jevEngine.ts`) | Один noul на ввімкнену категорію: `Does this item have the following drawback: "дефект екрану" (e.g. "тріснутий екран", "зламаний екран")?` + та сама межа «так/ні». Чи давати приклади — перевірити `npm run jev:probe` (скіл `jev-pilot`) на «macbook m1»: «лише назва» vs «назва + приклади». Упевненість, що приклади допомагають, — середня |
| ZIP ручного режиму | Ключі `patterns.json` — назви категорій; синоніми — підказка для regex у `prompt.txt`. `analyze.py` без змін |
| Генерація критеріїв | Промпт отримує наявні категорії з синонімами: «вже є — не повторюй і не перефразовуй». На фронті згенероване, що збігається з назвою/синонімом, поглинається наявною категорією |
| Перевірка / запис | Без змін: пишеться назва категорії |

**Перераховувати аналіз не треба:** об'єднання — це перейменування пунктів, інформація не губиться (було «тріснутий
екран» → стало «дефект екрану»). Новий прогін — за бажанням людини, щоб Jev/LLM спрацювали на категорії (AI —
лише за кнопкою).

### 4. UI (обрані варіанти)

```
Меню пошуку ⋮:  Редагувати · Фільтри · Варіанти · ▶ Критерії AI · Проект · Архів · Видалити
```

```
┌ Критерії пошуку · macbook m1 ──────────── ✕ ┐
│ [Мінуси 14]  [Плюси 9]          🔍 фільтр   │
│ [Додати свій критерій…__________] [＋]      │
│ [✨ Згенерувати] [Ще варіанти] [Вручну]     │
├─────────────────────────────────────────────┤
│ ☐ ● дефект екрану         у 41 огол.  ✎ 🗑  │
│      тріснутий екран ✕ · зламаний екран ✕   │
│ ☐ ● експлуатований        у 37 огол.  ✎ 🗑  │
│ ☐ ○ 8 GB оперативної пам'яті у 19     ✎ 🗑  │
│ ── лише в оголошеннях (не в списку) ──      │
│ ☐   подряпини на кришці   у 4 огол.    ＋   │
├─────────────────────────────────────────────┤
│ Обрано 2   [Об'єднати в категорію…] [Видал.]│
└─────────────────────────────────────────────┘
● / ○ — «в аналізі» увімкнено / вимкнено (перемикач)
```

```
┌ Об'єднати в категорію ───────────────┐
│ Назва: [дефект екрану__________]     │  ← підставлено найкоротшу з обраних
│ Синоніми: тріснутий екран · зламаний │
│ Зачепить оголошень: 41               │
│              [Скасувати] [Об'єднати] │
└──────────────────────────────────────┘
```

- Порожній пошук (критеріїв ще немає): у списку — підказка «Згенеруй або додай вручну»; згенеровані LLM
  додаються як нові категорії (увімкнені), а формулювання, що збігаються з наявною назвою чи синонімом, поглинаються.
  Зберігається одразу (`PUT /criteria`), без кроку «Далі». Логіку генерації/імпорту винести зі
  `useAnalysisCriteria` у спільний хук — її використовують і діалог, і майстер.
- Діалог із меню пошуку може відкритись для невибраного пошуку: оголошення для лічильників підтягуються
  `useListings(open ? id : null)` — так само, як у `SearchFiltersDrawer`.
- «Лише в оголошеннях» — пункти, що є в `listings.<mode>`, але не в списку (старі прогони, ручний едіт): їх можна
  додати (＋) або обрати для об'єднання.
- Майстер, крок 1: чипи = усі категорії режиму; обраний = `enabled`; у підказці чипа — синоніми, бейдж `+N`;
  посилання «Керувати критеріями…» відкриває діалог. «Далі: пошук» зберігає `enabled` і додані, нічого не видаляючи.
- Після `remap` — інвалідація запитів `listings`, `filter-options`, `criteria`.

## Перевірка

- `npm run check` (typecheck + Vitest + docs:check + skills:check), `npm run build`.
- Vitest: старий формат → групи; дублі назва/синонім відхиляються; `remapBullets` (дедуп, регістр, порядок,
  видалення); парс matching зводить синонім до категорії; промпт і Jev-питання містять синоніми; remap на тимчасовій
  БД — змінено лише зачеплені рядки, перейменовано local_filters, перераховано `filtered_out`.
- Ручні test-cases (локально, `npm run dev`, пошук «macbook m1»):
  0. Новий пошук без критеріїв → меню «⋮» → «Критерії AI» (майстер не відкривався) → «Згенерувати» і додати свій →
     закрити й відкрити знову — критерії на місці; майстер на кроці 1 показує їх обраними.
  1. Меню «⋮» → «Критерії AI» (і хаб AI → «Критерії») → видно всі мінуси й плюси з лічильниками; «лише в оголошеннях» показує пункти поза списком.
  2. Обрати «експлуатований» + «б/в стан» → «Об'єднати» → назва «б/в стан» → у таблиці колонка «Мінуси» показує
     «б/в стан» без дублів; лічильник збігся з «зачепить N».
  3. Локальний фільтр «Мінуси: експлуатований» до об'єднання → після — фільтр «б/в стан», кількість прихованих
     оновилась.
  4. Видалити «8 GB оперативної пам'яті» з галочкою «з оголошень» → зник у списку й таблиці; частина оголошень
     з'явилась у «Найкращих кандидатах».
  5. Вимкнути ○ категорію → майстер: чип не обраний; «Далі: пошук» → категорія лишилась у вікні.
  6. Крок 2 LLM і Jev → у «Перевірці» лише назви категорій; Jev-тост з вартістю.
  7. «Згенерувати критерії» → формулювання, що збігаються з синонімами, не з'являються окремими чипами.
- Прод: лише після злиття в `main` за «так» людини; Turso-бекап перед першим `remap` на проді — за рішенням людини.
