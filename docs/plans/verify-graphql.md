## Контекст

### Проблема

- Verify-прохід («Перевірити неактивні») відкривав сторінку кожного оголошення. З 2026-10-03 OLX (CloudFront) відповідає
  `403` на будь-яку HTML-сторінку → кнопку вимкнено ([verify-403-guard](old/verify-403-guard.md)).
- Вікно покриття (auto-disable зниклих) працювало лише для повного скану однієї видачі. Split-скан (розбиття за ціною) і
  скан із синонімами завжди частковий (`partial`) — вимкнення зниклих для великих пошуків не запускалося взагалі.

### Що перевірили 2026-10-25 (живі запити до OLX, паузи 1,5 с)

| Проба | Результат |
| --- | --- |
| Сторінка оголошення через `curl` (Schannel — інший TLS-стек, ніж Node) | `403` CloudFront |
| `curl` із повним набором браузерних заголовків | не запускали: агентний класифікатор заблокував як обхід бот-захисту; ідею P-005 (`curl-impersonate`) відкинуто з тієї ж причини |
| GraphQL: запит оголошення за id (`ad`, `offer`, `listing`, `adById`, `clientCompatibleListing`…) | немає (`GRAPHQL_VALIDATION_FAILED`, підказки приховані; ліміт аліасів — 5) |
| GraphQL: ключі `ids`, `ad_id` | ігноруються мовчки (видача — вся OLX, ~13 млн) |
| `query` = точна назва живого оголошення 866343231 | `200`, 1 результат — саме воно, `user.id` = 312402193 |
| `user_id` = 312402193 | `200`, 52 оголошення, усі цього продавця |
| `query` = назва давно зниклого 925673682 | 0 результатів |
| `user_id` магазинів MyApple / MacZone | 134 / 119 оголошень (4 сторінки на продавця) |
| **Після реалізації:** `npm run scan -- --search 1 --verify` (локальна копія, «ipad 9») | 50 запитів: живих 8, промахів 29, без вердикту 13, помилок немає; ліміт спрацював, `seller_id` дозаповнено 8 рядкам |
| Повнота пошуку за назвою: 8 точно живих оголошень (з видачі «ipad 9», назви зі `•`, `”`, `;`, дужками) | знайдено 8 з 8 |
| 29 промахів проти топ-1000 видачі «ipad 9» | жодного у видачі (узгоджується з «зникли»; не доказ — видача 2975, глибше не дивились) |
| **Після реалізації:** `npm run scan -- --search 2 --deep` (локальна копія, «macbook m1», 18 синонімів) | 140 запитів, знайдено 978 (нових 263), усі варіанти вичерпано → повне покриття спрацювало; промах отримали 530 рядків, вимкнено 0 (перший промах); `seller_id` записано всім побаченим |
| 8 випадкових промахів «macbook m1» → пошук за назвою | живих 0 з 8 (більшість востаннє бачені 2026-10-05) — хибних промахів у вибірці немає |

### Оцінка вартості (локальна копія прод-БД від 2026-10-23, пошук «macbook m1»)

| Показник | Значення |
| --- | --- |
| Оголошень у пошуку | 1246 |
| Кандидатів verify (не бачені > 3 днів до останнього скану, auto/rejected) | 889 (487 business / 402 private) |
| Різних продавців серед кандидатів (за іменем — нижня межа) | ≥ 360; з одним кандидатом — 241 |
| Варіантів запиту (синоніми) | 18; глибокий скан 2026-10-05 — 155 запитів |

Темп ≈ 3 с на запит (паузи як у глибокому скані):

| Сценарій | Запитів | Час |
| --- | --- | --- |
| Глибокий скан «macbook m1» (18 варіантів) | ≈ 155 | ≈ 8 хв |
| Verify лише через видачу продавця (усі кандидати мають `seller_id`) | ≈ 600–750 | ≈ 30–40 хв |
| Перший verify після релізу (`seller_id` немає → пошук за назвою, 1 запит на оголошення) | ≈ 890 | ≈ 45–50 хв |

> Виправлення в сесії: спершу глибокий скан оцінено в ≈ 35–45 запитів (одна видача); фактично — 18 синонімів, 155.

Висновки, з яких випливає поєднаний варіант:
1. Видача продавця не працює для старих рядків: кандидати — саме ті, кого скан не бачить, тож `seller_id` їм не допишеться.
2. Видача продавця майже не економить запити (більшість продавців — один кандидат; магазин — кілька сторінок).
3. Повний глибокий скан уже проходить усю видачу пошуку — вимикати зниклих може він, без додаткових запитів.

## Що зроблено (механіка — [business-rules](../business-rules.md) §3, запити — [olx-api](../olx-api.md) §2.12)

### Частина 1 — повне покриття глибоким сканом

- `FetchSearchResult.priceCoverage` — ціновий діапазон, який видача пройшла повністю: вичерпаний `fetchSearch` →
  діапазон фільтра пошуку; вичерпаний split (усі бакети, бісекція не обірвана, жоден бакет не `ListingError`, без
  `capHit`, не зупинено) → від нижньої межі (фільтр або 0) до зондованої максимальної ціни.
- Синоніми (`fetchAllQueries`, `runDeepScanFromPlan`): перетин покриттів усіх варіантів; хоч один неповний чи збій → немає.
- `finalizeScanResult`: частковий скан із `priceCoverage` → `applyScanStatuses(..., exhausted, 2, priceCoverage)`:
  кандидати лише з ціною в діапазоні (інша валюта — лише без меж; без ціни — лише від 0), поріг 2, у `warning` —
  «повне покриття: зниклі отримали промах…».
- Вичерпання за лічильником: сторінка, на якій закінчується `visible_total_count`, буває повною (count кратний 40) —
  тепер теж «вичерпано» (split-бакет і deep `fetchSearch`), інакше повне покриття губилося б часто.
- UI: рядок із `miss_count > 0` (не disabled) — блідий з іконкою й підказкою «Промах N з 2…»; нотатка в зведенні
  скану «Повна видача: зниклі отримали промах»; попередження аналізу — «Зниклі — лише за повного покриття».

### Частина 2 — GraphQL-verify для залишку

- `listings.seller_id` (`user.id`; запит скану тепер `user { id name }`), upsert — COALESCE.
- `scraper/graphql/verifyProbe.ts`: видача продавця (`user_id`, до вичерпання, запобіжник від ігнорування фільтра) і
  пошук за назвою (1 сторінка); `GraphqlClient.fetchByParameters`.
- `runVerify`: кандидати P1 = промахи (будь-який статус, крім disabled) + давно не бачені auto/rejected, промахи
  першими; P2 = без опису. Видача продавця вичерпана без оголошення → disabled (`auto-disabled: verify seller-feed`);
  не знайдено за назвою → промах, 2 поспіль → disabled (`auto-disabled: verify miss_count=2`). До 50 запитів;
  ліміт і «без вердикту» → `warning`, збій GraphQL → `error`. `VerifyResult.reactivated` → `missed`.
- HTML-пробу (`scraper/verifier.ts`), запобіжник `403` і перемикач `VERIFY_PROBE_AVAILABLE` прибрано; кнопка активна.

## Test-cases

Vitest (тимчасова БД, без запитів до OLX):

1. `statusEngine`: повне покриття — у діапазоні 1-й скан промах, 2-й disabled з позначкою coverage.
2. `statusEngine`: ціна поза діапазоном; без ціни при діапазоні не від 0; інша валюта при обмеженому діапазоні — не кандидати.
3. `priceCoverage`: діапазон від 0 містить оголошення без ціни; перетин варіантів — найвужчий спільний.
4. `scanFinalize`: частковий скан із `priceCoverage` рахує промахи, без нього чи зупинений — ні.
5. `split`: бакет із count, кратним 40, вичерпано; бакет із `ListingError` — повного покриття немає.
6. `normalizer`: `seller_id` пишеться й не затирається порожнім; дозаповнення існуючому рядку.
7. `verifyScan`: у видачі продавця → живе, `miss_count=0`, опис дозаповнено.
8. `verifyScan`: видача вичерпана без оголошення → disabled з позначкою; manual interested — без змін, manual rejected — disabled.
9. `verifyScan`: один запит на кількох кандидатів продавця; невичерпана видача → пошук за назвою.
10. `verifyScan`: за назвою знайдено → `seller_id`; не знайдено → промах, 2-й → disabled; видача > сторінки → без вердикту.
11. `verifyScan`: disabled не кандидат, свіжий промах — кандидат; ліміт запитів → `warning`; збій GraphQL → `error`.

Ручні (людина; локально `npm run dev` → http://localhost:5173 або прод після релізу):

12. Пошук із синонімами → «Сканування та статистика» → «Аналіз перед скануванням» → у попередженнях — «Зниклі — лише за
    повного покриття» (наведи на ⓘ — пояснення) → «Запустити» → після завершення в «Останній скан» — нотатка «Повна
    видача: зниклі отримали промах» (якщо скан пройшов усе) або «Авто-вимкнення зниклих пропущено» (якщо ні).
13. Таблиця цього пошуку → рядки, яких не було у видачі, — бліді, біля назви помаранчева іконка; наведи → «Промах 1 з 2…».
    Повтори глибокий скан → ці рядки (якщо так і не з'явились) мають статус «Неактивне», у нотатці — `auto-disabled: coverage miss_count=2`.
14. «Сканування та статистика» → картка «Перевірити неактивні» активна, в описі — «Шукає промахи (бліді рядки)…» без
    «HTTP 403» і P-005 → натисни → смуга прогресу з етапом «Перевірка живості · #… · видача продавця / пошук за назвою» →
    тост «Перевірку завершено · Перевірено … · промахів …».
15. Відкрий посилання 2–3 оголошень, які після перевірки стали неактивними (нотатка `verify seller-feed` або
    `verify miss_count=2`), у браузері → OLX показує, що оголошення неактивне / не знайдено.
