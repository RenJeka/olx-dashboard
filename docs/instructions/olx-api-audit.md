# Аудит запитів до OLX

## Коли застосовувати
Треба перевірити, чи OLX нічого не змінив: скан чи дерево категорій поводяться дивно, перед релізом змін у
`server/src/scraper/`, або періодично. Людина просить «перевір API OLX», «чи живі запити до OLX».

## Що робити
1. `npm run olx:audit` у корені репозиторію (за замовчуванням запит `iphone`; інший — `-- --query "<слово>"`).
   Живі запити до OLX — по одному на кожен запит застосунку, з паузами звичайного скану; перелік і що звіряється —
   [план olx-api-audit](../plans/olx-api-audit.md) → «Контекст», код — `server/src/scraper/audit.ts`.
2. Показати людині таблицю зі stdout (запит · HTTP (еталон) · тип · структура) і висновок:
   - усі ✅ (код виходу 0) — OLX нічого не змінив;
   - ❌ — під таблицею список полів: `−` зникло (OLX прибрав чи перейменував), `+` нове. Розбір —
     [olx-api](../olx-api.md) §5 «Чекліст «OLX щось поміняв»».
3. Розбіжність підтверджено (не разовий збій) → запис у журнал [olx-api](../olx-api.md) §6 (дата · що змінилось ·
   фікс або «відкрито»).
4. Еталон (`server/src/scraper/olxAuditEtalon.json`) оновлювати лише після рішення людини:
   `npm run olx:audit -- --update` — прийняти поточні відповіді як норму (напр. HTML знову віддає `200`).

## Чого не робити
- Не запускати в циклі чи частіше, ніж потрібно: кожен прогін — живі запити до OLX (ввічливість — `AGENTS.md` →
  «Інваріанти»).
- Не оновлювати еталон, щоб «позеленіти»: так ховається реальна зміна на боці OLX.
- `--update` з нестандартним `--query`: шляхи необов'язкових полів (напр. `location.district.name`) можуть випасти
  й дати хибні `−` наступного разу. Еталон — на запиті за замовчуванням.

## Як перевірити
Прогін без змін на боці OLX — таблиця з ✅ у кожному рядку й «Усе збігається з еталоном.».
