# Дизайн модулів

Модуль нижнього шару дає прості примітиви й не знає, хто його кличе; політика (що саме, для кого, яке
повідомлення) живе у викликача. Історія рішень — [`refactor-audit/audit.md`](refactor-audit/audit.md).

## Перероблені модулі

### Ручний порядок — `server/src/db/repos/manualOrder.ts`

| Примітив | Що робить |
|---|---|
| `ManualOrderList { table, groupColumn?, neighborFilter? }` | опис впорядкованого списку: таблиця з `sort_order`, група сусідів, фільтр сусідів |
| `nextTopSortOrder(list)` | `sort_order` для нового елемента згори |
| `moveOneStep(list, id, direction)` | обмін із сусідом; `false` — елемента немає |
| `isDirection(value)` | перевірка `'up' \| 'down'` |

**Де політика:** опис списку — у репозиторії сутності (`PROJECT_ORDER` у `repos/projects.ts`, `SEARCH_ORDER` у
`repos/searches.ts`); перевірка напряму, тексти помилок і що повернути після руху — у `services/`.
Новий впорядкований список = нова константа `ManualOrderList` поруч із його таблицею, без нових функцій.

## Чотири питання для нового коду

1. Який найпростіший інтерфейс покриває всі поточні потреби?
2. У скількох ситуаціях використовуватиметься функція? Одна ситуація й назва викликача в імені — ознака
   спеціалізації.
3. Чи легко нею користуватися для поточних задач? Якщо кожен викликач пише ті самі рядки — винеси їх у тонку
   функцію верхнього шару.
4. Чи відокремлено загальне від специфічного? Нижній модуль не знає сторінок, кнопок і текстів UI.

Без коду «на майбутнє»: параметри, реєстри й плагінні точки, яких ніхто не використовує, не додаємо.
